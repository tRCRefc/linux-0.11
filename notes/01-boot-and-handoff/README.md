# 阶段一：UEFI 启动与内核交接

提交区间：`057ec45..3690495`，日期：2026-08-01。

这一阶段解决的不是进程或内存分配，而是先建立一条不依赖传统 BIOS 启动扇区的 x86-64
执行路径，并把 CPU、栈、描述符表和页表逐步交给内核自己管理。

## 启动责任的转移

执行路径可以压缩为：

```text
OVMF
-> efi_main
-> 获取内存图
-> ExitBootServices
-> x86_64_start
-> 内核栈
-> 自有 GDT/IDT
-> 自有 CR3
-> x86_64_kernel_main
```

UEFI 是平台脚手架，替代原版 `bootsect.s/setup.s` 的硬件进入方式；内核拥有自己的栈、描述符表
和页表，则是在新架构上重新承担原版 `head.s` 的责任。学习时应区分这两类代码，不能把“由
固件送入 long mode”描述成“内核已经完成全部早期初始化”。

## 页表选择

启动页表用 2 MiB 大页恒等映射前 4 GiB。这样只需：

```text
1 PML4 + 1 PDPT + 4 PD = 6 pages
```

它让指令地址、栈指针、全局数据和串口 MMIO 在切换 CR3 时保持有效。代价是权限粒度较粗，
因此后续用户页、COW 页和精细权限必须使用独立的 4 KiB 页表路径。

## 这一阶段的证据

串口继续输出到 C 入口证明：

- EFI ABI 和位置无关入口能够运行；
- `ExitBootServices` 后没有继续调用固件服务；
- 自有栈能够承载 C 调用；
- 新 CR3 下代码、数据、栈、GDT、IDT 仍可访问。

它不能证明物理页可分配、用户权限正确或页异常可恢复。这些属于后续阶段。
